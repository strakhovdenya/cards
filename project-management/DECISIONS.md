# Architecture Decisions

Здесь фиксируются решения, которые не стоит передоговаривать заново при каждой следующей задаче.
Одно решение — один раздел. Формат намеренно короткий: что решили, почему, откуда взялось.

Файл читается автоматически вместе с корневым `CLAUDE.md` (он ссылается на него через `@`), так
что всё записанное здесь попадает в контекст каждой сессии — пиши по делу.

## Формат

```markdown
## ADR-NNN — Короткое название решения

Status: `Accepted` | `Superseded by ADR-MMM`

Decision:
Что именно решено, в настоящем времени и конкретно.

Reason:
Почему так, и какая альтернатива отвергнута.

Source: кто/когда/в каком контексте (issue, PR, разговор с датой).
```

## ADR-001 — Автономный цикл Ralph создаёт PR, но никогда не мёрджит

Status: `Accepted`

Decision:
Автономный агент (`.claude/ralph/`) реализует issue и создаёт PR, но мёрдж всегда выполняет
человек, посмотрев Vercel preview этого PR. Агент не имеет доступа к `git commit`/`push`/`gh` —
все мутации git/GitHub делает контроллер детерминированным кодом.

Reason:
`main` автоматически деплоится в прод, автотестов в проекте нет, поэтому единственная реальная
проверка поведения — человек на preview. Автоматический мёрдж убрал бы эту проверку целиком.
Отсутствие git/gh у агента заодно устраняет класс «агент сам себе расширил права».

Source: перенос механизма из `jobflow-cv-pipeline`, 2026-09-17.

## ADR-003 — Сборка не требует серверных секретов Supabase

Status: `Accepted`

Decision:
Сервисный клиент Supabase (Service Role Key) создаётся лениво, при первом обращении —
`getServiceSupabase()` в `src/lib/supabase.ts`. Ни один модуль не создаёт клиент и не проверяет
`SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` на верхнем уровне. Отсутствие конфигурации — ошибка
конкретного запроса, а не ошибка сборки. В CI эти две переменные намеренно не задаются, чтобы
регресс был заметен сразу.

Ключ Service Role **не** добавляется в окружение Preview на Vercel: preview-URL публичные, а
ключ даёт полный доступ к боевой базе в обход RLS. Preview собирается и открывается; серверные
роуты, которым нужен этот клиент, на preview отвечают ошибкой — это осознанный компромисс.

Reason:
Раньше клиент создавался при вычислении модуля и бросал исключение без переменных. Next собирает
page data для API-роутов на этапе сборки, то есть импортирует этот модуль, — поэтому сборка
требовала боевых секретов, а в Vercel они заданы только для Production. Итог: **каждый**
preview-деплой падал с "Failed to collect page data for /api/cards". Это убивало единственную
реальную проверку поведения перед мёрджем, поскольку автотестов в проекте нет.

Альтернатива «просто добавить ключи в Preview» отвергнута: она чинит симптом ценой раздачи
service-role-доступа публичным preview-URL.

Source: issue #4, найдено при подключении CI, 2026-09-17.

## ADR-002 — Изменения схемы Supabase применяет только человек, и только аддитивно

Status: `Accepted`

Decision:
SQL-схемы и миграции (`docs/**/*.sql`) правит и применяет человек вручную в Supabase SQL editor.
Автономному агенту путь `docs/**` закрыт на уровне permissions, и он обязан ответить
`BLOCKED-DB-CHANGE`. Порядок выкатки изменения данных: аддитивная миграция → код → выкатка →
отдельной задачей удаление старого.

Reason:
Supabase — один и тот же проект для прода и для preview-деплоев, поэтому ломающая миграция роняет
живое приложение немедленно, ещё до мержа связанного PR. Откатить её так же быстро нельзя.

Source: перенос механизма из `jobflow-cv-pipeline`, 2026-09-17.

## ADR-004 — Единственная система стилей — MUI

Status: `Accepted`

Decision:
Tailwind CSS удалён из проекта полностью: пакеты `tailwindcss` и `@tailwindcss/postcss`,
`postcss.config.mjs` и `src/app/globals.css`. MUI (тема в `ThemeProvider.tsx` + `CssBaseline`) —
единственный источник глобальных стилей. Фон страницы, цвет текста и шрифт берутся из темы MUI
(`palette.background.default` = `#f5f5f5`, `palette.text.primary`, стек
`"Roboto", "Helvetica", "Arial", sans-serif`), а не из правил, которые были в `globals.css`.
Полутёмная тема по `prefers-color-scheme`, которая раньше подмешивалась через `globals.css`,
убрана — это было багом (страница темнела вслед за ОС, а компоненты MUI оставались светлыми).
Если понадобится глобальное CSS-правило, ему место в `MuiCssBaseline.styleOverrides` внутри
`ThemeProvider.tsx`, а не в отдельном CSS-файле.

Reason:
В проекте было две системы стилей одновременно, хотя Tailwind нигде не использовался (ни одного
`className` в `src/`) — он остался от шаблона `create-next-app`. Emotion-кеш MUI вставляется в
начало `<head>` (`prepend: true`), поэтому `globals.css` шёл после него и перебивал `CssBaseline`
на `body`, из-за чего фон и шрифт расходились с темой, а в тёмной теме ОС возникала смесь светлых
MUI-компонентов на тёмном фоне.

Отвергнутые альтернативы:

- оставить обе системы и развести конфликт порядка CSS через CSS layers — не решает, что Tailwind
  всё равно не используется, лишь маскирует конфликт;
- перенести правила `body` из `globals.css` в тему 1:1 (`#fff`, Arial) — сохраняет расхождение
  фона/шрифта с уже существующей темой MUI ради «пиксель в пиксель» с прежним (багованным)
  поведением.

Source: issue #5, 2026-09-17.

## ADR-005 — Rate limiting: Upstash Redis с in-memory деградацией

Status: `Accepted`

Decision:
Rate limiting на публичных `guest=1` API-эндпоинтах и на `/auth/**` (`src/proxy.ts`) реализован
через `checkRateLimit()` в `src/lib/rate-limit.ts`: основной путь — sliding window через
Upstash Redis (`@upstash/ratelimit` + `@upstash/redis`), общий счётчик на все Edge-инстансы.
Если `UPSTASH_REDIS_REST_URL`/`UPSTASH_REDIS_REST_TOKEN` не заданы, либо вызов к Redis падает
с ошибкой или таймаутом (1.5s), лимитер откатывается на in-memory sliding window
(`checkRateLimitInMemory`) — счётчик в этом случае локален для конкретного Edge-инстанса,
эффективный лимит на пользователя может быть выше заявленного при трафике, размазанном по
нескольким инстансам. Лимиты: 60 req/min для guest API, 20 req/5 min для auth. Заголовок
`Retry-After` — в ответе 429. Реальные вызовы Supabase Auth (signIn/signUp) идут
браузер → Supabase напрямую и покрываются встроенным rate limiting Supabase — дублировать
на уровне Next.js нет смысла.

Reason:
Issue #15 рекомендует именно Upstash Redis, и `UPSTASH_REDIS_REST_URL`/`UPSTASH_REDIS_REST_TOKEN`
уже заведены в `.env` и на Vercel (Production + Preview) — заводить внешний сервис не требовалось,
только код. Первая реализация (агентом Ralph) ошибочно выбрала чистый in-memory вариант, приняв
решение без проверки реального `.env` (там переменных нет только в `.env.example`, который
коммитится). Чистый in-memory был отвергнут как основной путь: на serverless/Edge нет гарантии
одного инстанса на пользователя, поэтому реальный лимит мог оказаться в разы мягче заявленного.
Redis без какого-либо fallback тоже был отвергнут: недоступность Upstash не должна ронять
`/api` и `/auth` целиком — деградация до in-memory сохраняет хотя бы защиту от бёрстов в рамках
инстанса, вместо отказа обслуживания или пропуска лимита совсем.

Source: issue #15, 2026-09-18; пересмотрено в этом же PR после ревью, 2026-09-18.

## ADR-006 — Фабрика dark-factory подключена как внешний пакет по тегу

Status: `Accepted`

Decision:
Процессные скиллы, агенты, хуки, контроллер Ralph, Acceptance Verifier и Calibration Judge Cards
берутся только из установленного пакета `dark-factory`, закреплённого в `devDependencies` на тег
(на момент решения — `github:strakhovdenya/dark-factory#v0.1.3`, commit
`33fa44be6803ad8c2190c3a60cd6ce41ff42b5df`; текущий pin — в `package.json`/lock и CLAUDE.md).
Копии движка, реестра reason codes, хуков или workflow фабрики в репозитории не держатся: в
`.claude/` лежат только управляемые копии, которые раскладывает `setup.js` пакета (они в
`.gitignore`), а в `.github/workflows/` — короткие обёртки reusable workflows. Commit в `uses@` и
`with.factory-sha` обёрток совпадает с commit тега в `package-lock.json`. Версия меняется только
отдельной задачей по `docs/upgrading.md` нового тега, без `npm update` и без правок
`node_modules/dark-factory`.

Проектные значения задаются одним файлом — `.factory/profile.json`: команды gate, защищённые пути,
`branchTemplate`, `verifier.checks`, `verifier.goldenDir`, `judge.enabled`, `ralph`. Trusted-конфиги
verifier и Judge (`.github/verifier/*.json`, `.github/calibration/*.json`), профиль и golden set
фабрика читает с default-ветки, а не из PR. Их изменение действует только после merge и не
проверяет PR, который его вносит.

Режимы и обязательные проверки:

- Acceptance Verifier работает в режиме advisory: `VERIFIER_ENFORCE` не задан, не-PASS вердикт не
  роняет статус, и в branch protection статус не требуется. Переход в enforce — отдельное решение
  владельца после подтверждённого eval и живого прогона, а не побочный эффект другой задачи.
- Calibration Judge включён (`judge.enabled: true`), но только наблюдает: разбирает раунд по метке
  владельца `calibrate` или по ручному запуску и не меняет вердикты, статусы и метки.
- CodeQL (`Analyze (javascript-typescript)`, job в `ci.yml`, advanced setup; CodeQL default setup
  остаётся выключенным) входит в обязательные CI-проверки `required-checks.json`; актуальный
  список — в самом `required-checks.json` и в CLAUDE.md, а не в ADR. Имена jobs
  меняются только вместе со списком: отсутствующее или неоднозначное имя verifier считает
  проваленной required check.

Принципы ADR-001 и ADR-002 сохраняются, теперь их обеспечивает контроллер пакета, а не код в
репозитории. Агент Ralph не имеет git/gh, PR создаёт контроллер, мёрдж делает только человек после
preview. `docs/` входит в `protectedPaths`, а задача со схемой БД получает `BLOCKED-DB-CHANGE` и
метку `ralph-needs-db-change`. Правила ADR-001/002 не меняются, меняется только место их
реализации: путь `.claude/ralph/` из ADR-001 заменён контроллером пакета, а закрытие `docs/**` из
ADR-002 задаётся `protectedPaths` профиля. Поэтому ADR-006 не заменяет ADR-001/002, а тексты
ADR-001…005 не переписываются и amendment-блоков не получают.

Фактические результаты golden eval и живых прогонов Ralph фиксируются в протоколе
`project-management/verification/factory-acceptance.md` (его создаёт задача приёмки #82), а не в
этом ADR. Само наличие подготовленного golden set результатом eval не считается.

Alternatives considered:

- Оставить в репозитории собственные копии скиллов, хуков и `.claude/ralph/` (состояние до #74) —
  отвергнуто: механизм, перенесённый из Jobflow (ADR-001, ADR-002), пришлось бы синхронизировать
  вручную, и по репозиторию нельзя было бы установить, какой версией проверок прошёл конкретный PR.
- Плавающая ссылка на фабрику (ветка, semver-диапазон, `npm update`) — отвергнуто: обёртки
  verifier/eval сверяют `factory-sha` с commit закреплённого тега и падают при расхождении, а
  плавающая версия делает вердикт невоспроизводимым.
- Читать trusted-конфиги и профиль из ветки PR — отвергнуто: PR смог бы ослабить проверки, которыми
  его же и проверяют (убрать required check, расширить allowlist моделей).
- Сразу включить enforce-режим verifier — отвергнуто: пока eval и живой прогон Ralph на Cards не
  подтверждены, блокирующий вердикт может остановить мёрдж из-за среды, а не PR. Пример — первый
  вердикт на PR #80 был FAIL из-за неготовой среды (не было отчёта модели, provenance и
  одобрения), а не из-за дефекта PR.
- CodeQL через default setup или отдельным workflow — отвергнуто в #76: default setup блокирует
  SARIF-загрузку advanced setup, а отдельный workflow даёт второе одноимённое имя check, которое
  verifier считает неоднозначным.

Reason:
Cards — второй потребитель фабрики после Jobflow. Единый закреплённый релиз даёт обоим проектам одни
и те же проверки, а каждое обновление проходит явной задачей. Trusted-данные с main и advisory-режим
до подтверждённой приёмки — это то же разделение, на котором держится ADR-001: решение о мёрдже
остаётся за человеком, пока автоматика не доказала себя на этом проекте. Список альтернатив
ограничен вариантами, которые реально сравнивались в #74–#76; другие способы распространения
фабрики (например, git submodule) не рассматривались и здесь не оцениваются.

Source: владелец проекта, подключение в #74–#76 (PR #78–#80, 2026-10-25), зафиксировано в #81
координатора #77, 2026-10-25.

## ADR-007 — Демо на общей оболочке, прогресс гостя на устройстве, запись только через `getUser()`

Status: `Accepted`

Decision:

- Гость `/demo` и вошедший пользователь используют одни компоненты `AppShell` (шапка, контент,
  нижняя навигация) и `StudyNavigation` (меню «Изучение»). Список шести учебных экранов задан один
  раз в `src/utils/navigationUtils.ts` (`STUDY_SCREENS`). `DemoApp` — только контейнер гостевых
  данных. Отдельный демо-интерфейс не заводится. В гостевом дереве не монтируются редакторы,
  импорт, менеджер тегов, приглашения и `UserMenu`; вкладка «Редактирование» видна и `disabled`.
  Это проверяют компонентные тесты `src/components/DemoApp.test.tsx` по маркерам этих компонентов.
- Отметка «Выучено» гостя хранится только в localStorage браузера (`useDemoProgress`, ключ
  `cards:demo-progress:v1`, формат `id → boolean`) и накладывается на загруженные демо-карточки.
  На сервер, в общие демо-данные и в личный аккаунт она не попадает и при входе не переносится.
  `useDemoProgress` импортирует только `DemoApp`, а `UniversalCardViewer` получает обработчик
  `onGuestToggleLearned`, а не хранилище. Это ограничение импортов проверяется ревью диффа,
  отдельного автоматического стража у него нет.
- Право записи решает `src/lib/auth-server.ts`. `getAuthenticatedUser()` подтверждает
  пользователя через `auth.getUser()` (сервер Supabase Auth), а не через `getSession()`. Каждый
  изменяющий handler в `src/app/api` (POST/PUT/PATCH/DELETE) первым действием вызывает
  `getAuthenticatedUser({ mode: 'write' })` и превращает отказ в ответ через
  `authErrorResponse()`. Нет подтверждённого пользователя или проверка упала — 401. Подтверждённый
  `DEMO_USER_ID` в режиме записи — 403. Флаги запроса (`guest`, `user_id`, `role`, `isGuest`),
  Origin и Referer прав не дают. Собственных проверок сессии, `guest` или `DEMO_USER_ID` в
  изменяющих handlers нет. Новый изменяющий экспорт в `src/app/api` автоматически попадает под
  тест `src/app/api/demo-access.test.ts`, который обходит каталог и сверяет набор с матрицей.
- Гостевое чтение (`?guest=1`) допускается только в GET-обработчиках, только через
  `getServiceSupabase()` и только с фильтром `user_id = DEMO_USER_ID`; без заданного
  `DEMO_USER_ID` гостевой GET отвечает 500, а не читает без фильтра. Перечень таких маршрутов
  ведётся в коде и CLAUDE.md, а не в этом ADR. Rate limit этих запросов по-прежнему задаёт ADR-005.

Alternatives considered:

- Сохранить отдельный демо-интерфейс с горизонтальными вкладками и доработать его под телефон —
  отвергнуто владельцем: он расходился с приложением, не помещался на узком телефоне и показывал четыре
  экрана из шести.
- Открыть гостю серверный `PUT` для «Выучено» — отвергнуто: демо-данные общие для всех
  посетителей, и отметка одного гостя стала бы видна всем.
- Включать гостевую отметку по факту переданного `toggleLearnedService` — отвергнуто владельцем
  2026-10-29: при `isGuest` серверные сервисы игнорируются, а существующие тесты «guest toggle
  sends no request» и «guest cannot toggle learned» остаются стражами без переписывания.
- Оставить `getSession()` и проверять `DEMO_USER_ID` в каждом handler — отвергнуто: `getSession()`
  читает cookie без проверки сервером Auth, а разнесённые по handlers проверки легко пропустить в
  новом маршруте.

Reason:
Демо — витрина портфолио, поэтому гость должен видеть то же приложение, что и пользователь, в том
числе на телефоне. Чем больше экранов открыто гостю, тем важнее, чтобы запрет записи не зависел от
интерфейса. Прод и preview делят одну базу (ADR-002, ADR-003), и сессия демо-аккаунта могла бы
менять общие демо-данные, поэтому ей отказывает сервер. RLS по-прежнему защищает строки от чужих
ID; эта проверка — дополнительный слой, а не замена RLS. Цена решения — лишний запрос к Supabase
Auth на каждом авторизованном API-вызове. Это серверная проверка уже выданной сессии; вызовы
signIn/signUp по-прежнему идут браузер → Supabase и покрываются его встроенным лимитом, поэтому
лимиты ADR-005 не меняются.

Source: владелец проекта, решения 2026-10-29, issue #126.
