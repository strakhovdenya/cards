**PRD:** `project-management/prd/PRD-core-flows-reliability.md`
**Date:** 2026-10-26 (редакция 2: сверка с актуальным PRD R1–R8, переработана фаза 4, добавлены матрица исходов, зависимости, ручная приёмка и условия готовности)

Условные обозначения: **[ручной]** — выполняет человек, Ralph не передаётся; **[код]** — задача кода (исполнитель определяется проверкой возможностей Ralph, см. ## Implementation Phases

Для каждой фазы указаны **обязательные зависимости** (без них задача технически невозможна или даст неверный результат) отдельно от **рекомендуемой последовательности** (только чтобы уменьшить конфликты файлов; нарушение допустимо). Это же сведено в таблице после списка фаз.

### Phase 0: Ручная подготовка — тестовый пользователь, тестовые данные, факты о живых данных
**Goal:** Дать последующим фазам среду для безопасных ручных проверок на общей базе (прод и preview делят один проект Supabase) без зависимости от исправленного редактора карточек (Phase 3) и подтверждённые факты о данных. Кода нет; фаза идёт параллельно Phase 1–2.
**Affects:** Supabase (общий проект: Auth, данные тестового пользователя; для фактов о данных — только чтение); репозиторий не меняется.
**Tasks:**
- [ ] **0.1 [ручной]** Подтвердить доступный способ создать тестового пользователя, не предполагая его заранее: (а) приглашение администратором через существующий `InviteManager` + регистрация (в `proxy.ts` есть ворота приглашений на `/auth/signup`); (б) создание пользователя в Supabase Auth dashboard. Для выбранного способа проверить, что строка `profiles` создаётся триггером `handle_new_user` (`docs/03-setup-triggers.sql`) и что вход в приложение под этим пользователем работает. Учётные данные не коммитятся
- [ ] **0.2 [ручной]** Наполнить тестовые данные способами, которые работают **на текущем коде** (без правок редактора): (а) массовый импорт обычных карточек и существительных (`BulkImport`/`BulkNounImport` идут через `/api/cards/bulk`, который уже сохраняет `word_type`/`grammar_data`) — даёт карточки и существительные с артиклем/множественным числом; (б) `TagManager` для тегов и назначение тегов импортом; (в) глаголы — существующий `VerbEditor` (режим редактирования → глаголы) или импорт глаголов; (г) статусы «выучено»/«не выучено» — существующая кнопка в учебном экране. Только если нужного набора этим не получить, допустим прямой INSERT человеком в SQL editor — **но сначала проверить, что способ вообще доступен**: триггер из `docs/apply-user-isolation-fix.sql` выставляет `user_id = auth.uid()`, а в SQL editor `auth.uid()` пуст, поэтому вставка может записать пустой `user_id` или упасть; отключать триггеры или менять схему для этого нельзя (ADR-002). Готовые скрипты копирования данных (`docs/copy-user-data.sql` и подобные) как предпосылку не использовать: они привязаны к конкретным UUID и не проверялись на пригодность. Минимальный набор: ≥10 карточек (из них ≥3 существительных с артиклем и множественным числом, ≥1 без `word_type`/`grammar_data`), ≥3 тега и карточки с 0, 1 и несколькими тегами, ≥3 глагола, часть карточек «выучена»
- [ ] **0.3 [ручной]** Read-only запросом в SQL editor установить фактические значения `cards.word_type`, форму `cards.grammar_data` и применено ли ограничение `check_word_type`; записать результат комментарием в issue задачи 3.2

**Done when:** выполнены предпосылки PRD «Dependencies» п. 5 и п. 6; способ получения пользователя и данных записан (какой из перечисленных реально сработал), набор данных проверен чтением под тестовым пользователем; результат 0.3 доступен задаче 3.2 (PRD, R1.11: «Перед реализацией человек подтверждает read-only запросом фактические значения `word_type` и формы `grammar_data` в общей базе»). Обязательных зависимостей нет.
**Ручная приёмка:** сама фаза — ручная; проверка — вход под тестовым пользователем на preview любого PR или на production (авторизованные маршруты работают с `NEXT_PUBLIC_SUPABASE_*`, сервисный ключ не нужен).

### Phase 1: Tracer bullet — горячие клавиши не мешают вводу (и первые компонентные тесты)
**Goal:** Закрыть High-замечание P1-002 и пройти путь «DOM-окружение → компонентный тест → общая проверка адресата клавиши» на одном экране, затем на остальных. Первая фаза с кодом; инфраструктура вводится вместе с первым реальным тестом, а не отдельной задачей.
**Affects:** cards: `src/components` (UniversalCardViewer, VerbStudy, VerbViewer, SpeechButton), общая проверка адресата события (`src/utils` или `src/hooks`), `vitest.config.ts` (`include` для `.tsx`, DOM-окружение), `package.json`/`package-lock.json` (DOM-библиотека — выбор в задаче), `CLAUDE.md` (раздел тестов). Конфигурация инструментов и манифест должны быть названы в `Affects` issue — иначе граничная проверка Ralph даст BLOCKED. Учесть ограничение Ralph (`ralph/README.md`): агент не устанавливает пакеты, зависимости синхронизирует контроллер после последнего прохода агента, поэтому агент не сможет сам запустить компонентные тесты на новой библиотеке до синхронизации; исполнитель задачи 1.1 определяется проверкой по правилам 4.1 (по умолчанию — человек/интерактивная сессия).
**Tasks:**
- [ ] **1.1 [код]** Общая проверка «событие адресовано полю ввода / `contenteditable` / элементу внутри диалога / кнопке» + подключение DOM-окружения и `.tsx`-тестов + применение в `UniversalCardViewer` (Enter/Space на кнопке, ввод в диалоге, статус «выучено» не меняется); компонентные тесты падают на текущем коде
- [ ] **1.2 [код]** Применить ту же проверку в `VerbStudy`, `VerbViewer`, `SpeechButton` с компонентными тестами; обновить раздел тестов в `CLAUDE.md`

**Done when:** закрывает R3.1 («Нажатия клавиш, адресованные `input`, `textarea`, `select`, `contenteditable` и любым элементам внутри открытого диалога, не вызывают горячих действий»), R3.2 («`Enter` и `Space` на сфокусированной кнопке выполняют действие кнопки»), R3.3 («При открытом диалоге… ни одно нажатие не меняет статус „выучено“ скрытой карточки» на всех четырёх экранах); общий критерий готовности задач кода выполнен. Обязательных зависимостей нет.
**Ручная приёмка:** preview PR, узкий вьюпорт и десктоп; под тестовым пользователем (0.1–0.2): открыть «Управление тегами»/импорт поверх учебного экрана, набрать «das Haus ist fast» + Enter — текст цел, статус карточки не менялся; Enter на кнопке «Перемешать».

### Phase 2: Единая обработка ошибок API, модель исходов и видимость фоновых ошибок
**Goal:** Любая ошибка API превращается в читаемое сообщение; сервисы возвращают типизированный результат с четырьмя исходами (включая «результат неизвестен») и сверку состояния с сервером; фоновые сбои (удаление, загрузка) видны на своём экране. Основа — существующий #69 (см. раздел «Существующие issue»).
**Affects:** cards: `src/services/*` (общий разбор ответа вместо четырёх копий `handleApiResponse`, типизированный результат), `src/hooks/useCards.ts`, `useVerbs.ts`, `src/components/AuthenticatedApp.tsx` (экранные ошибки, «повторить»), тесты сервисов и компонентов. БД не затрагивается.
**Tasks:**
- [ ] **2.1 [код]** Общий разбор ответов сервера, устойчивый к не-JSON (HTML 502/504, пустое тело) и к отклонённому `fetch` (после отправки запроса такой сбой для мутации = **неизвестный результат**, а не отказ); замена копий `handleApiResponse` в сервисах карточек, существительных, тегов, глаголов; юнит-тесты
- [ ] **2.2 [код]** Типизированный результат мутаций с исходами «успех / частичный успех (`failed[]`, `tagsAttached`, признак частично применённой правки) / подтверждённый отказ / неизвестный» в `cardService` и `verbService` без изменения формы `ApiResponse<T>` и существующих сигнатур (новые методы или расширенный результат); общая операция «сверка с сервером» (перечитать сущность/список) для исхода «неизвестный»; юнит-тесты
- [ ] **2.3 [код]** Фоновые операции на экране: ошибка **удаления карточки** (отказ — сообщение, карточка остаётся; неизвестный результат — не убирать и не считать удалённой, перечитать список, затем показать фактический итог; повторное удаление безопасно: контракт `DELETE` — 200 для отсутствующей), ошибка загрузки списка отличается от пустого и имеет «повторить»; уведомления не перекрываются нижней навигацией; компонентные тесты

**Done when:** закрывает R6.2 («Ответ сервера не в JSON… даёт читаемое русское сообщение вместо `Unexpected token '<'`»), R6.3 («Сбой загрузки списка карточек/глаголов отличается от пустого списка»), R1.6 («При ошибке удаления пользователь видит сообщение на экране, карточка остаётся в списке»), а для операции «удаление карточки» — исходы по матрице (раздел «Матрица исходов»); создаёт основу R7.1–R7.5 для остальных фаз. Обязательные зависимости: Phase 1 (компонентные тесты). Рекомендуемая последовательность: первой после Phase 1.
**Ручная приёмка:** preview PR под тестовым пользователем в узком вьюпорте: удаление при отключённой сети (DevTools offline после отправки — неизвестный результат), при неверной сессии (отказ), загрузка списка при блокировке `/api/cards` (ошибка ≠ пусто); уведомление не под нижней навигацией.

### Phase 3: Редактор карточек — сохранность данных и честный результат
**Goal:** Тип слова, базовая форма и грамматика сохраняются при создании и правке; окно редактора не теряет ввод и закрывается только по подтверждённому успеху; результат создания и правки различает четыре исхода.
**Affects:** cards: `src/app/api/cards/route.ts`, `src/app/api/cards/[id]/route.ts`, `src/app/api/cards/bulk/route.ts` (только валидация), единый маппер ответов, `src/services/cardService.ts`, `src/hooks/useCards.ts`, `src/components/CardEditor.tsx`, `AuthenticatedApp.tsx`; тесты route handlers (подмена `getAuthenticatedUser()` и возвращаемого клиента), сервиса и компонента. БД не затрагивается.
**Tasks:**
- [ ] **3.1 [код]** Единый DB→DTO маппер карточки во всех обработчиках; `PUT` сохраняет и возвращает `word_type/base_form/grammar_data`; `PUT` для отсутствующей/чужой карточки → 404; контракт `DELETE` (200 для отсутствующей) закреплён тестом и комментарием в описании issue; route-тесты
- [ ] **3.2 [код]** Базовая серверная валидация `word_type` (множество из `check_word_type`, уточнённое фактами 0.3) и `grammar_data` (JSON-объект, `article`/`plural` — строки, прочие ключи не отбрасываются) в `POST`, `PUT`, bulk; карточки без этих полей остаются рабочими; route-тесты
- [ ] **3.3 [код]** Клиент передаёт `CardFormData` целиком в `createCard`/`updateCard` и хук; список после правки совпадает с перезагрузкой; юнит-тесты сервиса
- [ ] **3.4 [код]** `CardEditor`: асинхронные колбэки; по исходам (матрица): успех — закрытие; отказ — окно открыто, ввод цел, причина внутри формы; частичный (создана без тегов) — предупреждение `tagsAttached: false`, окно закрывается после показа результата; неизвестный — ввод цел, сообщение «результат неизвестен», перечитывание списка и сверка (слово появилось → считать выполненным и не отправлять повторно); блокировка отправки на время запроса; компонентные тесты
- [ ] **3.5 [ручной]** Приёмка на preview (см. ниже)

**Done when:** закрывает R1.1 («Создание карточки передаёт на сервер тип слова, базовую форму и грамматические данные»), R1.2, R1.3, R1.4 («При ошибке создания/обновления… окно редактора остаётся открытым, значения сохранены»), R1.5, R1.9 (`PUT` → 404; контракт `DELETE` не меняется и закреплён тестом), R1.11, R1.12, R2.3 («Создание одиночной карточки с `tagsAttached: false` сопровождается предупреждением „создана без тегов“»), а для операций «создание» и «правка полей» — исходы по матрице, R7.6(а) (повтор последовательно) и граница R7.6(б). Обязательные зависимости: Phase 1 (компонентные тесты), Phase 2 (разбор ошибок, модель исходов, сверка), задача 0.3 (факты для 3.2). Рекомендуемая последовательность: после Phase 2; до Phase 4, 5 (общие файлы маршрутов карточек).
**Ручная приёмка:** preview PR, тестовый пользователь, узкий вьюпорт: создать существительное с артиклем и множественным числом → открыть заново → значения на месте → слово есть в тренажёре артиклей; правка артикля; ошибка 409 (дубликат); сеть пропала после отправки (неизвестный результат).

### Phase 4: Атомарная замена тегов (P1-005)
**Goal:** Изменение тегов карточки либо применяется целиком, либо прежние связи сохраняются; карточка с недопустимыми тегами не создаётся; случай «поля сохранены, замена тегов отклонена» показывается как частичный результат. Единственная фаза с изменением БД. Порядок задач фиксирован: сначала выяснить, кому можно отдавать работу, затем согласовать контракт, затем реализовать.
**Affects:** Supabase (новая аддитивная функция Postgres; `docs/*.sql` — файл готовит и применяет человек, ADR-002), cards: `src/app/api/cards/[id]/route.ts`, `src/app/api/cards/route.ts`, обработка ответа в сервисе/хуке/`CardEditor` для частичного результата; тесты route handlers и компонента.
**Tasks:**
- [ ] **4.1 [ручной] Проверка возможностей Ralph и распределение работ фазы — до назначения любого исполнителя.** Сверить актуальное состояние: версия `dark-factory` против закреплённого тега (`package.json`/lock) и против меток в удалённом репозитории; `node_modules/dark-factory/ralph/README.md` и руководства этой версии; `.factory/profile.json` (`protectedPaths`, `humanNeededVerdict`, `labels.humanNeeded`, `agentEnvironment`, `sandbox`, команды гейта); `.claude/settings.json` (permissions и хуки); CLAUDE.md, ADR-002, ADR-006. Без изменения БД. Результат записывается в issue фазы 4 таблицей по задачам 4.2–4.6: **«можно передать Ralph» / «нужен человек»**, основание и **условия, обязательные перед запуском** (например: контракт зафиксирован и одобрен в теле issue; функция уже применена и проверена; в `Affects` названы все изменяемые файлы и конфигурации; тело issue прямо сообщает, что функция уже существует и SQL не требуется; метки `ralph-*` не ставятся вручную). Правило неопределённости: если вывод по задаче не удаётся обосновать документами и профилем — задача **не** считается готовой для Ralph. ## Правила декомпозиции Cards

Прод живой, а Supabase общий для прода и preview, поэтому фазы режутся так, что приложение остаётся рабочим после каждой из них.

- Миграция схемы БД — отдельной первой задачей фазы, которая её требует. Её выполняет и применяет человек вручную в Supabase SQL editor (ADR-002), правки идут в `docs/*.sql`. Автономный агент Ralph по такой задаче отвечает `BLOCKED-DB-CHANGE`, поэтому задачи кода от неё отделяй и ставь после неё.
- Миграция в плане только аддитивная (новая таблица, новый nullable-столбец, новая политика). Ломающее изменение (`DROP`, `RENAME`, сужение типа, ужесточение `NOT NULL`) раскладывай по фазам: аддитивная миграция → код, работающий с новым вариантом → выкатка → удаление старого отдельной фазой после переключения кода и выкатки нового.
- Фаза не может требовать от кода схему, которой в базе ещё нет, и не может убирать из базы то, чем ещё пользуется задеплоенный код.
- Каждая фаза проходит `npm run check` и `npm run test`, а мобильный вид и демо-режим (только на чтение) не ломаются между фазами.

Применение в этом плане: единственная миграция — аддитивная функция в Phase 4. Перед ней стоят проверка возможностей Ralph (4.1) и согласование контракта (4.2), затем сама миграция (4.3) и проверка (4.4), и только потом код (4.5); «удаление старого» после неё не требуется (ничего не удаляется). Остальные фазы схему не меняют.
