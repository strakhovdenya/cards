# Тестовый пользователь для ручных проверок (#91)

Протокол создания отдельного пользователя для ручной приёмки мутаций (редактор, импорт, замена
тегов, учебная сессия, недействительная сессия). Контекст: PRD `PRD-core-flows-reliability.md`,
Dependencies, п. 5; план — Phase 0, задача 0.1. Наполнение данными — #92, факты о
`word_type`/`grammar_data` — #93; схема, триггеры и RLS-политики этой задачей не менялись (ADR-002).

Прод и preview делят один проект Supabase, поэтому пользователь заведён один раз и доступен на
обеих средах.

## Граница безопасности

- Тестовый пользователь **не** демо-пользователь: его `id` не равен `DEMO_USER_ID` (сверено при
  создании). Он также не реальный пользователь: адрес заведён только для проверок.
- Ручные мутации (создание, правка, удаление карточек, тегов, глаголов, импорт) допустимы **только**
  под этим пользователем. Под реальными аккаунтами и под демо-пользователем их не делают.
- Роль в `profiles` — `user`. Адрес главного администратора из триггера `handle_new_user`
  (`docs/03-setup-triggers.sql`) для тестового пользователя не используется.
- Пароль, ключи и токены в репозиторий не попадают. Пароль хранит владелец вне репозитория.

## Способы создания

Регистрация закрыта приглашениями: ворота на `/auth/signup` в `src/proxy.ts` требуют действующий
`?invite=<код>`. Профиль в `profiles` создаёт триггер `handle_new_user` при вставке в `auth.users`.

| Способ                                                                 | Итог                 | Причина                                                                                                                                                      |
| ---------------------------------------------------------------------- | -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Admin API Supabase Auth (`POST /auth/v1/admin/users`, `email_confirm`) | **Сработал, выбран** | Пользователь создан с подтверждённым адресом; триггер создал строку `profiles`. Не требует письма и входа администратора в приложение. Выполнено 2026-10-29. |
| Приглашение через `InviteManager` и регистрация по `/auth/signup`      | Не проверялся        | Требует входа администратора в приложение и письма/ссылки; для одного тестового адреса избыточно. Остаётся штатной альтернативой для повторения.             |
| Создание в Supabase Auth dashboard (Authentication → Users → Add user) | Не проверялся        | Требует ручных действий в интерфейсе; результат эквивалентен выбранному способу (та же вставка в `auth.users`, тот же триггер).                              |

Выбранный способ — Admin API. Он штатный механизм Supabase Auth, не меняет схему, триггеры и
политики (INV-1), но использует серверный ключ, поэтому выполняется только человеком или по его
прямому поручению.

## Проверка

Дата: 2026-10-29. Среда: production-проект Supabase (общий для production и preview).

- Адрес: тестовый алиас владельца (в протоколе не приводится), подтверждён при создании.
- Строка `profiles` создана триггером: `role = user`, `id` совпадает с `auth.users.id`.
- Вход по email и паролю выполнен через Supabase Auth (`grant_type=password`): ответ 200, выдан
  токен сессии для этого `id`. Вход через форму `/auth/login` на preview или production
  **не проверялся** — его выполняет владелец (см. «Ручная проверка владельцем»).

## Находка: временные политики открывали чужие данные (исправлено)

Под сессией тестового пользователя (без собственных данных) запрос на чтение через anon-ключ с
его токеном вернул строки других владельцев:

| Таблица | Строки чужих владельцев                | Строки демо-пользователя |
| ------- | -------------------------------------- | ------------------------ |
| `cards` | 683 (выборка ограничена 1000 строками) | 317                      |
| `tags`  | 18                                     | 14                       |
| `verbs` | 0                                      | 0                        |

Причина: на `cards` и `tags` оставались временные политики из ранних схем
(`Allow all operations temporarily` и `Allow all operations on tags temporarily`, `ALL`, `true`,
роль `public`), перекрывавшие политики «только свои строки». Владелец удалил обе политики
(`DROP POLICY`) вручную в SQL editor 2026-10-30.

Повторная проверка после удаления (2026-10-30): под сессией тестового пользователя чужих и
демо-строк в `cards`, `tags` и `verbs` нет (0), анонимный запрос к `cards`, `tags` и `verbs`
возвращает 0 строк, публичная страница и гостевой `GET /api/cards?guest=1` отвечают штатно.
Политики остальных таблиц `public` просмотрены целиком (`pg_policies`), RLS включён на всех. Открытые политики
на `cards` и `tags` и на `profiles` исправлены выше; прочие находки вынесены в отдельные задачи.

## Находка: политики `profiles` (исправлено)

В живой базе политика `UPDATE` на `profiles` не ограничивала колонки (вошедший пользователь мог
изменить свою `role`), а политика вставки допускала `WITH CHECK (true)` для роли `public`.
Владелец 2026-10-30 вручную удалил обе политики и ограничил обновление `profiles` колонками
`first_name` и `last_name` (права на колонки плюс политика своей строки). Проверка под тестовым
пользователем после этого: смена `role` отклонена (403, `permission denied`), смена имени
проходит и возвращена обратно, анонимная вставка в `profiles` отклонена политикой RLS.
Администратор в `profiles` один — владелец. Регистрация через триггер `handle_new_user` не
затронута: функция `SECURITY DEFINER`, владелец `postgres`, `force_rls = false`.

## Как повторить

1. Решите, какой адрес использовать: не адрес администратора из триггера и не адрес реального
   пользователя. Для Gmail подходит `имя+метка@gmail.com`, если ящик ваш.
2. Создайте пользователя одним из способов:
   - Auth dashboard: Authentication → Users → Add user, укажите адрес и пароль, отметьте
     подтверждение адреса;
   - Admin API: `POST <SUPABASE_URL>/auth/v1/admin/users` с заголовками `apikey` и
     `Authorization: Bearer <серверный ключ>` и телом
     `{"email": "<адрес>", "password": "<пароль>", "email_confirm": true}`; ключ берите из своего
     окружения и не сохраняйте в файлах репозитория;
   - приглашение: администратор создаёт приглашение в `InviteManager`, получатель открывает
     `/auth/signup?invite=<код>`.
3. Проверьте строку: в SQL editor `select id, email, role from public.profiles where email = '<адрес>';`
   должна вернуться одна строка с ролью `user`.
4. Сверьте, что `id` не равен значению `DEMO_USER_ID`.
5. Войдите в приложение через `/auth/login` на preview или production и запишите дату и среду
   здесь же.
6. Храните пароль в менеджере паролей; в репозиторий, issue и PR его не добавляйте.

## Ручная проверка владельцем

- Войти через форму `/auth/login` на preview любого открытого PR под тестовым пользователем.
- Убедиться, что под тестовым пользователем видны только его данные (после удаления временных политик).
