# Issues Generator — cards

Прочитай план из файла: $ARGUMENTS

Если `$ARGUMENTS` не указан — спроси у пользователя путь к файлу плана
(`project-management/plan/PLAN-<kebab-name>.md`), не выдумывай его.
Если файл не найден — сообщи об этом и останови выполнение.

Для каждой фазы плана создай milestone, а для каждой задачи внутри фазы — Issue в GitHub,
используя `gh` CLI.

Эти GitHub issues — **источник правды для создания и выполнения задач**. Они не запускают
реализацию сами по себе: работа над конкретным issue идёт либо вручную через Branch-first
protocol из корневого `CLAUDE.md`, либо автономно через Ralph loop (`.claude/ralph/`), который
читает тело issue как спецификацию. Из-за второго формат Body ниже — не косметика: контроллер
Ralph парсит именно раздел `## Acceptance Criteria` (чек-лист `- [ ]`), чтобы сверить самоотчёт
агента и отметить выполненные пункты.

Этот скил — не единственный способ завести issue: для одиночной задачи вне эпика (нет PRD/плана)
issue создаётся тем же форматом Body напрямую через `gh issue create`, без плана — план/milestone
нужны только когда несколько задач объединены в фазы. В этом случае источником для
`Docs to Read`/`Key Invariants`/`Affects` становится не PRD (его нет), а прямое чтение затронутого
кода — раздел "Сверка с реальным кодом" ниже применяется тем более строго.

## Перед созданием — проверка на дубли

`gh` не даёт создавать issues идемпотентно — при повторном запуске скила на том же плане нужно
самому не создавать дубли:

- `gh api repos/:owner/:repo/milestones --paginate` — проверь, нет ли уже milestone с таким же
  заголовком (`<epic> · Фаза N: название`), прежде чем создавать новый.
- `gh issue list --search "in:title <текст задачи>" --state all` — проверь, нет ли уже issue с
  таким же заголовком, прежде чем создавать новый.

Если что-то уже существует — пропусти создание и сообщи об этом в итоговой сводке, не создавай
дубль и не спрашивай пользователя по каждому отдельному совпадению.

## Порядок действий

1. Прочитай файл плана целиком (все секции `### Фаза N: ...`), а также PRD, на который план
   ссылается в шапке (`**PRD:** ...`) — целиком, не только заголовки. Issue Body требует полей
   (`Docs to Read`, `Key Invariants`, `Test Requirement`), которых нет в самом плане — они
   берутся из PRD, не выдумываются. Идентификатор эпика бери из H1 плана; если явного нет —
   используй короткое kebab-имя фичи из имени файла плана.
2. Для каждой фазы создай milestone, **с префиксом эпика в заголовке** — без этого при нескольких
   параллельных эпиках разные milestones «Фаза 1: …» неразличимы:
   ```
   gh api repos/:owner/:repo/milestones -f title="<epic> · Фаза N: название" -f description="Цель фазы (из '**Цель:**' плана)"
   ```
3. Для каждой задачи (строка `- [ ] ...` под `**Задачи:**`) внутри фазы — **перед тем как
   зафиксировать текст её issue** — выполни два обязательных шага (разные задачи одной фазы обычно
   затрагивают разные файлы, так что оба шага делаются отдельно для каждой задачи):
   - сверь файлы, которые попадут в её `Affects`, с реальным кодом (см. "Сверка с реальным кодом");
   - если сверка выявила развилку реализации — спроси пользователя и зафиксируй ответ в
     `Key Invariants` (см. "Развилки реализации") — не переноси открытую развилку в issue.
4. Создай Issue для этой задачи, привязанный к её milestone:
   ```
   gh issue create --title "..." --body "..." --label "..." --milestone "<epic> · Фаза N: название"
   ```
5. После создания всех issues выведи сводку: сколько milestones/issues создано, сколько пропущено
   как дубли, ссылки на созданные issues.

## Сверка с реальным кодом (обязательна перед фиксацией текста issue)

План и PRD пишутся *до* погружения в детали реализации — они не могут знать про расхождения,
видные только в самом коде (например: хук уже возвращает данные в другой форме, в кодовой базе
уже есть стратегия/сервис, который надо переиспользовать, а не дублировать). Поэтому, прежде чем
писать финальный текст `Affects`/`Docs to Read`/`Key Invariants`:

- Открой и прочитай фактически каждый файл, который попадёт в `Affects` — не по памяти о плане.
- Проверь, что упомянутые сигнатуры/пути всё ещё актуальны — план мог быть написан раньше кода.
- Явно выпиши любые расхождения между "как в плане" и "как в коде" — не подгоняй Body молча.
- Если в затронутом коде уже есть готовый паттерн/хелпер для того, что требует задача — укажи его
  прямо в `Affects`, чтобы исполнитель переиспользовал его, а не изобретал второй способ рядом.

## Развилки реализации — уточняй у пользователя заранее

Если для задачи есть больше одного одинаково валидного способа реализации — **не оставляй эту
развилку в issue открытой** ("можно так или так") и не рассчитывай, что исполнитель сам её удачно
разрешит. Автономный агент Ralph на такой формулировке обязан ответить `BLOCKED`, то есть задача
просто не поедет.

Вместо этого: сформулируй развилку и её варианты и спроси пользователя (`AskUserQuestion`).
Получив ответ, зафиксируй его в `Key Invariants` явной пометкой:

```
**Resolved decision (do not re-litigate/ask):** <выбранный вариант> — <краткая причина>.
Отвергнутая альтернатива: <вариант> — <почему не он>.
```

Если после сверки с кодом и разбора развилок честная неопределённость остаётся — не создавай
issue в текущем виде; сначала проясни недостающее с пользователем.

## Формат Issue

Цель формата — чтобы issue можно было взять в разработку, не открывая ни план, ни PRD, и чтобы
автономный агент мог реализовать его без человека рядом.

**Title**: текст задачи из плана дословно, без квадратных скобок `- [ ]`.

**Body**:
```markdown
## Контекст
{Цель фазы (из "**Цель:**" плана) в 1-2 предложения + как эта задача в неё вписывается}

## Affects
{конкретные файлы/пути — `src/components/...`, `src/services/...`, `src/hooks/...`. Если план
даёт только общее направление, а PRD называет конкретные файлы — используй более конкретный
источник. Этот список используется и как скоуп для code-review: находки на файлах вне него
считаются out-of-scope и не чинятся в рамках этой задачи}

## Docs to Read
{конкретные секции/файлы для чтения перед реализацией — не общие фразы. Если ничего специфичного
нет — впиши только то, что реально применимо, не заполняй поле ради заполнения}

## Key Invariants
{неочевидные правила, которые нельзя нарушить именно в этой задаче: совместимость со схемой
Supabase, поведение demo-режима (гость = read-only), обратная совместимость уже задеплоенного
кода. Включай только применимое к этой задаче. Развилки — пометкой
`**Resolved decision (do not re-litigate/ask):** ...`}

## Acceptance Criteria
{чек-лист `- [ ]`, по одному проверяемому пункту на строку. Формулируй так, чтобы по каждому
пункту можно было назвать конкретный файл/проверку — по этому списку автономный агент пишет
самоотчёт, а контроллер отмечает чек-боксы}

## Test Requirement
{что и как проверяется. Автотестов в проекте пока нет, поэтому обычно это: `npm run check`
(lint:strict + format:check + tsc) и `npm run build`, плюс — если задача меняет UI или поведение —
ручная проверка на Vercel preview этого PR, записанная комментарием на этот же issue. Если задача
требует живой Supabase/браузера, укажи это явно: автономный агент такой пункт выполнить не может
и обязан честно пометить его `NOT VERIFIED`}

## Definition of Done
- [ ] Acceptance Criteria выше выполнены
- [ ] `npm run check` зелёный
- [ ] `npm run build` зелёный (если изменения могут влиять на сборку)
- [ ] Если поменялась структура/архитектура — корневой `CLAUDE.md` обновлён в том же PR

## Dependencies
{"Depends on #NNN" / "Blocks #NNN" — ссылки на другие issues; если зависимостей нет — напиши
"Нет" явно, не пропускай секцию. Для Ralph это же отношение дублируется в `dependsOn` его
конфига}

---
Сгенерировано из `<путь к файлу плана>` (PRD: `<путь к PRD из шапки плана>`).
```

Если для конкретного поля в PRD/плане реально нет информации — оставь короткую явную пометку
("не указано в PRD"), не выдумывай содержимое и не удаляй секцию молча: пропавшая секция читается
как "не нужно", а не как "не найдено".

Для ad-hoc issue без плана/PRD footer заменяется на `Создано как отдельная задача (без
плана/PRD).` — не оставляй плейсхолдер незаполненным.

**Label**: выбирай только из уже существующих в репозитории лейблов (`gh label list`) — не
создавай новые без явного запроса. По умолчанию: `enhancement` для задач реализации,
`documentation` для задач, которые правят только `docs/`/`project-management/` без кода.
Лейблы `ralph-blocked` / `ralph-needs-db-change` ставит только контроллер Ralph — вручную их
не проставляй.

**Milestone**: заголовок фазы с префиксом эпика, созданный на шаге 2.

## Правила

- Не меняй и не удаляй сам файл плана — скил только читает его.
- Не создавай issues для фаз/задач, которых нет в файле плана — не придумывай новый скоуп.
- Один milestone на фазу, ровно так, как фазы разбиты в плане.
- Footer в конце Body обязателен всегда — это единственная прослеживаемость обратно к PRD.
- Не запускай `gh pr create`, не переключай ветки и не коммить ничего — это только issue-трекер.
