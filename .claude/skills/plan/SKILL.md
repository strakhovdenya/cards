# Plan Generator — cards

Прочитай PRD: `$ARGUMENTS` — если это путь к файлу, читай напрямую; если это kebab-case имя
фичи, ищи в `project-management/prd/PRD-$ARGUMENTS.md`.

Если PRD-файл не найден — сообщи об этом и останови выполнение, не выдумывай содержимое PRD.

Создай план реализации и сохрани в `project-management/plan/PLAN-<kebab-name>.md` (то же
kebab-case имя, что и у PRD). Если нет папки `project-management/plan/` — создай её.

Этот план — черновая раскладка PRD на фазы, а не сами GitHub issues. Следующий шаг —
`.claude/skills/issues`, который заводит каждую фазу как milestone, а каждую задачу — как issue.

## Структура плана

```markdown
# Plan: {название фичи}

**PRD:** `project-management/prd/PRD-<kebab-name>.md`
**Дата:** {текущая дата}

## Фазы реализации

### Фаза 1: {название}
**Цель:** Что даёт эта фаза
**Затрагивает:** конкретные пути — `src/services/...`, `src/components/...`, `src/hooks/...`,
`docs/*.sql` (если нужна миграция)
**Задачи:**
- [ ] Задача 1
- [ ] Задача 2

**Когда готова:** закрывает пункт(ы) `## Критерии готовности` PRD: "{дословная или близкая цитата
конкретного AC-пункта}". Не пиши расплывчатый критерий вроде "работает нормально" — только то,
что можно проверить и что явно ведёт к конкретному AC из PRD.

### Фаза 2: {название}
...
```

## Правила разбивки на фазы

- Каждая фаза должна давать рабочий результат.
- Фазы независимы, можно остановиться после любой.
- Первая фаза — минимальный рабочий путь (Tracer Bullet).
- Не больше пяти задач в одной фазе.
- **Миграция схемы Supabase — всегда отдельная, первая задача фазы**, и она выполняется
  человеком вручную (автономный агент её делать не может и обязан ответить
  `BLOCKED-DB-CHANGE` — см. `.claude/ralph/README.md`). Код, зависящий от новой колонки/таблицы,
  идёт задачей после неё, не в одной с ней.
- **Аддитивность важнее красоты.** `main` автоматически деплоится на Vercel, а Supabase общий для
  прода и preview. Планируй порядок фаз так, чтобы после каждой фазы живое приложение оставалось
  рабочим: сначала аддитивное изменение, потом переключение кода, потом отдельной фазой — удаление
  старого. Не ставь удаление старого поля/компонента в ту же фазу, что и введение нового.
- Тесты (если PRD их требует) — часть той же задачи, что меняет код, а не отдельная задача
  "написать тесты" в конце фазы.

## Самопроверка перед сохранением файла

Перед тем как записать файл плана — перечитай черновик и сверь с PRD:

- Каждая фаза закрывает конкретный пункт `## Критерии готовности` PRD — открой PRD и найди
  пункт дословно, не по памяти.
- Все AC из PRD в сумме покрыты какой-то фазой — ни один не потерян и не задвоен без причины.
- Любая ссылка на файл/раздел — открыта и подтверждена, не оценена на глаз.

## Правила

- План должен покрывать все пункты `## Критерии готовности` из PRD.
- Не добавляй задачи, которых нет в PRD — этот скилл раскладывает PRD на фазы, не придумывает
  новый скоуп.
- Если в PRD остались открытые вопросы (`## Открытые вопросы` не пуст) — задай вопрос
  пользователю перед созданием плана, а не строй план поверх неопределённости.
- Этот скилл не создаёт и не редактирует код, ветки, коммиты или GitHub issues — только сам файл
  плана.
