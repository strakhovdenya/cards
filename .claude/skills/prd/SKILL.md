# PRD генератор — cards

Создай PRD (Product Requirements Document) для следующей фичи: $ARGUMENTS

Сохрани результат в файл `project-management/prd/PRD-$ARGUMENTS.md` (переведи название фичи на
английский и kebab-case, например `PRD-spaced-repetition.md`).

Если нет папки `project-management/prd/` — создай её.

Этот PRD — не GitHub Issue. Это документ уровня "что и зачем", который предшествует им: после
согласования PRD с пользователем следующий шаг — `.claude/skills/plan` (разбить PRD на фазы),
затем `.claude/skills/issues` (завести фазы/задачи как milestones/issues на GitHub — источник
правды). Для фичи, умещающейся в один PR (не эпик — см. "Режим эпика"), задача заводится как один
GitHub Issue напрямую, тем же форматом (`.claude/skills/issues/SKILL.md`), без промежуточного
plan-файла. Не подменяй эти шаги — PRD не должен содержать детальный implementation-план.

## Перед тем как писать

Прочитай (кратко, только нужные секции — не файлы целиком):

- Корневой `CLAUDE.md` — разделы про структуру проекта, архитектурные правила и защиту прода.
- `project-management/DECISIONS.md` — проверь, не противоречит ли фича уже принятому решению
  (если противоречит — не игнорируй молча, вынеси в `## Открытые вопросы`).
- `docs/` — там лежат SQL-схемы и заметки по настройке Supabase (`database-schema*.sql`,
  `*-migration*.sql`, `README-database.md`). Если фича трогает данные — это обязательный
  источник, а не справочный.
- Открытые issues на GitHub (`gh issue list`) — не дублирует ли фича то, что уже в работе.

## Структура документа

```markdown
# PRD: {название фичи}

**Дата**: {текущая дата}
**Статус**: Draft
**Связанный issue**: {ссылка на существующий GitHub issue, если уже есть, либо "новая фича — ещё
не заведена как issue"}

## Цель

Одно-два предложения: что и зачем это нужно пользователю приложения (человеку, который учит язык
по карточкам).

## Контекст и согласованность с проектом

- Какой слой это затрагивает: `src/app` (роуты/страницы), `src/components` (UI),
  `src/hooks`, `src/services` (доступ к данным/Supabase), `src/strategies` (режимы
  тренировок/импорта), `src/lib`, `src/types`.
- Затрагивает ли демо-режим (`/demo`, гостевой доступ только на чтение через `DEMO_USER_ID`) —
  если да, опиши, как фича ведёт себя для гостя.
- Связанные решения из `DECISIONS.md` (одна строка сути), если фича продолжает или пересекается
  с уже принятым.

## Зависимости

Что должно уже быть сделано, прежде чем фича имеет смысл технически (реальная предпосылка, а не
"было бы неплохо"). Если явных нет — напиши "Явных зависимостей не найдено".

## Пользовательские сценарии

- Пользователь {действие} -> {результат}

## В скоупе

Конкретный список того, что входит в эту итерацию фичи.

## Не в скоупе

Явно то, что не делаем сейчас.

## Влияние на данные и схему Supabase

Новые/изменённые таблицы, колонки, RLS-политики; нужна ли SQL-миграция. **Обязательно отметь,
является ли изменение аддитивным или ломающим.** Supabase — один и тот же проект для прода и для
preview-деплоев, миграции применяются вручную в SQL editor, поэтому ломающее изменение схемы
роняет живое приложение сразу, ещё до мержа PR. Если ломающее изменение неизбежно — опиши порядок
выкатки (аддитивная миграция → код, читающий оба варианта → выкатка → отдельная задача на
удаление старого).

Если фича не трогает данные — напиши "Не применимо: схема не меняется."

## Влияние на UI

Какие экраны/компоненты меняются, как это выглядит на мобильном (приложение используется
преимущественно с телефона, есть bottom navigation). Если есть мокап/референс — сошлись на него.

## Ключевые инварианты

Неочевидные правила, ограничивающие реализацию. Проверяй в первую очередь:

- Демо-режим остаётся read-only: гость не может создавать/редактировать/удалять.
- Изоляция данных между пользователями (RLS) не ослабевает — см. `docs/`-заметки про
  user-isolation и card-tags security.
- Уже задеплоенный код продолжает работать после миграции (обратная совместимость).
- Границы слоёв: доступ к Supabase живёт в `src/services`, не в компонентах.

## Технические ограничения

Известные ограничения (Next.js App Router: server/client-компоненты; MUI + Tailwind сосуществуют;
env-переменные `NEXT_PUBLIC_*` инлайнятся на этапе сборки).

## Критерии готовности (Acceptance Criteria)

Проверяемые, конкретные пункты — этот список должен быть готов к прямому копированию в будущий
GitHub Issue `## Acceptance Criteria`.

- [ ] Критерий 1
- [ ] Критерий 2

## Test Requirement (набросок)

Автотестов в проекте пока нет, поэтому по умолчанию это `npm run check` + `npm run build` плюс
ручная проверка на Vercel preview соответствующего PR. Если фича достаточно логически сложная,
чтобы заслуживать реальных тестов, — скажи это явно здесь, отдельным пунктом.

## Открытые вопросы

Всё, что нужно уточнить у пользователя, прежде чем это можно оформить как задачу: неясности в
скоупе, конфликты с уже принятым решением, недостающие мокапы/данные.

## Документация, которую потребуется обновить

Если фича меняет структуру проекта, схему данных или правила работы — перечисли, что потребует
обновления: корневой `CLAUDE.md`, `DECISIONS.md`, `docs/*.sql`/`docs/*.md`, `README.md`.

## Предполагаемое дробление на подзадачи (только если это эпик)

{раздел появляется, только если см. "Режим эпика" ниже — иначе не включай его в файл вообще}

Черновой список тем для будущих задач — не сами задачи: их разбивает `.claude/skills/plan` на
фазы, а `.claude/skills/issues` заводит как GitHub issues.

1. {короткое название темы} — {одно предложение, что покрывает и какой AC из PRD закрывает}
2. ...

Если темы естественно зависят друг от друга (схема данных → сервис → UI) — перечисли в этом
порядке; это подсказка для последовательности.
```

## Режим эпика

Если фича по масштабу — эпик (несколько логически завершённых кусков, которые не имеет смысла
закрывать одним PR), включи секцию "## Предполагаемое дробление на подзадачи". Если фича
умещается в один PR — не включай эту секцию вообще (не оставляй пустой заголовок).

Не уверен, эпик это или нет — спроси пользователя явно, а не угадывай.

## Самопроверка перед сохранением файла

Перед тем как записать PRD-файл, перечитай собственный черновик и сверь его с источниками — не
полагайся на память о том, что только что прочитал:

- **Каждое утверждение о механике проекта** (как работает демо-режим, что делает конкретный
  сервис, какие колонки есть в таблице) — перепроверь дословно по файлу-источнику, а не по
  пересказу.
- **Каждая ссылка на файл/строку** — открой и подтверди, не оценивай на глаз.
- Если нашлась неточность — исправь до сохранения, не сохраняй черновик с известной ошибкой.

## Правила

- Пиши конкретно — никакой воды.
- Критерии готовности должны быть проверяемыми, без формулировок типа "работает хорошо".
- Не описывай, КАК реализовывать (код, конкретные файлы, шаги) — только ЧТО и ЗАЧЕМ.
- Если описание фичи короткое или неоднозначное — задавай уточняющие вопросы до полного
  понимания, прежде чем создавать файл.
- Явно проверяй фичу на конфликт с уже принятыми решениями в `DECISIONS.md`. Если конфликт есть —
  не замалчивай и не переписывай решение сам, вынеси в `## Открытые вопросы`.
- Этот скилл не создаёт и не редактирует код, ветки, коммиты — только сам PRD-файл.
