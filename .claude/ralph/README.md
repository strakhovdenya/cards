# Ralph Loop — детерминированный оркестратор + ограниченный кодящий агент

Автономный цикл: по списку GitHub issues с зависимостями (`dependsOn`) сам берёт следующий
готовый issue, реализует его и создаёт PR — без участия человека на каждом шаге. **Мёрдж PR
всегда делает человек вручную.**

Механизм перенесён из проекта `jobflow-cv-pipeline`, где он был отлажен на десятках живых
прогонов. Ниже — принципы, которые на этих прогонах оказались существенными, и то, чем эта
версия отличается под реалии `cards`.

## Ключевой принцип: Claude не управляет git/gh вообще

Вложенный `claude -p` **не имеет** прав на `git commit`/`push`, ни на что из `gh`. Его
единственная задача — отредактировать код в уже подготовленной директории, прогнать проверки и
завершить ответ ровно одним из трёх вердиктов:

```
DONE
TYPE: <feat|fix|docs|chore|refactor|test>
SUMMARY: <короткое описание>
```
```
BLOCKED: <причина>
```
```
BLOCKED-DB-CHANGE: <что и почему>
```

Всё остальное — выбор issue, base branch, клон, `npm install`, коммит, push, создание PR,
комментарии/лейблы на issue при `BLOCKED` — делает **контроллер** (`run.js`/`core.js`), обычным
детерминированным кодом.

Почему так: ранняя версия давала агенту git/gh внутри git worktree, и это оказалось хрупким —
агент то видел директорию пустой, то сообщал о заблокированном доступе, один раз просто завис.
Убрав у агента git/gh полностью и заменив worktree на обычный `git clone`, заодно устраняется
класс «агент отредактировал `settings.json`, чтобы обойти ограничение» — обходить просто нечего.

`BLOCKED` требуется и в двух неочевидных случаях: если что-то отклонено по правам доступа (не
пытаться обойти другим синтаксисом — это тот же самый отказ), и если для продолжения нужно
решение человека (неоднозначная формулировка issue, несколько разумных вариантов реализации).
Агент работает без присмотра — гадать хуже, чем остановиться.

## Линии защиты перед тем, как появится PR

Зелёные проверки **не доказывают**, что диф соответствует issue: на живых прогонах в доноре
повторялся паттерн «тесты зелёные, а Key Invariant issue тихо нарушен». Поэтому между вердиктом
`DONE` и коммитом стоят независимые проверки:

1. **Гейт по типу изменённых файлов** (`hasCodeChanges()`/`DOC_ONLY_PATH_PATTERNS`) — если диф
   целиком из `*.md`/`docs/**`, оба ревью пропускаются: у чистой доковой правки нет кодового
   инварианта, который можно тихо нарушить.
2. **Пост-DONE self-review** — отдельный `claude -p` с урезанными правами (только чтение и
   диагностика, никакого `Edit`/`Write`) и без общей памяти с реализатором. Проверяет буквальное
   соблюдение Key Invariants, выполнение AC по существу, риск false-negative у
   `toContain`-проверок, работу логики на реальных данных, дублирование источника правды.
   Вердикт: `REVIEW: PASS` / `REVIEW: FAIL: <что и где>`.
3. **Code-review пасс** через встроенный скилл `code-review` — покрывает то, что self-review
   намеренно исключает (корректность + переиспользование/упрощение/эффективность). Находки на
   файлах **вне** `## Affects` текущей issue не чинятся, а уходят комментарием в tech-debt
   tracker (issue #1) — чинить вслепую код чужой закрытой задачи опасно.
4. **Финальная `npm run check`/`npm run build` перед коммитом** (`runVerificationChecks()` в
   `core.js`, безусловно, если диф не doc-only) — контроллер сам перепроверяет собранность
   финального состояния дерева, не доверяя ни самоотчёту агента, ни вердиктам self-review/
   code-review о том, что «сборка сейчас красная, но это ожидаемо». Красный build здесь — это
   `BLOCKED`, PR не создаётся.

   Добавлено после живого инцидента на ISSUE-28 (2026-09-18): PR ушёл с падающим
   `npm run build` (Next.js 16 E900 — одновременно существовали и `middleware.ts`, и
   `proxy.ts`), хотя реализатор корректно пометил старый файл маркером `DEL_RALPH:` и
   self-review/code-review видели этот маркер и полагались на то, что контроллер его
   обработает. Корневая причина найдена и воспроизведена: `applyDelRalphMarkersIfAny()`
   не переименовал файл ни разу за весь прогон, потому что её `findDelRalphMarkedFiles()`
   ловила ЛЮБУЮ ошибку `fs.readFileSync` в `catch { continue; }` и трактовала её как «файл
   удалён» — включая транзиентные `EPERM`/`EBUSY`, которые на Windows иногда возникают у
   отдельного Node-процесса сразу после того, как в этой же папке только что упал
   `npm run build` (воспроизведено вживую на этой машине: обычный `node -e` в том же шелле
   один раз словил `Permission denied` сразу после `next build` и тут же отработал заново
   без единого изменения кода). Ошибка проглатывалась молча — ни строки в логе, ни
   `BLOCKED`, просто нулевой результат раз за разом. Исправлено на двух уровнях:
   `findDelRalphMarkedFiles()` теперь делает короткий retry (до ~350мс) на любой ошибке
   чтения, кроме `ENOENT`, и логирует, если файл так и не читается после повторов; а этот
   финальный build-гейт — независимый предохранитель на случай, если DEL_RALPH всё равно
   промолчит по любой другой причине.

`FAIL` не означает сразу `BLOCKED`: находка уходит на точечный фикс (ещё один `claude -p` с
возвращёнными правами на Edit/Write), после чего ревью прогоняется заново. У каждого пасса свой
бюджет попыток (`MAX_REVIEW_FIX_ATTEMPTS` / `MAX_CODE_REVIEW_FIX_ATTEMPTS`, по 2). Только
исчерпание бюджета, `BLOCKED` от фиксера или нераспарсенный вердикт дают настоящий `BLOCKED`:
коммита/PR не будет, issue получает лейбл `ralph-blocked`, чтобы не быть тихо выбранной повторно.

## Чем эта версия отличается от донорской

- **Один пакет в корне репозитория**, а не `apps/api`+`apps/web`: контроллер делает один
  `npm install` в корне клона.
- **Гейт верификации — `npm run check`** (lint:strict + format:check + tsc) и `npm run build`.
  Тестов в проекте пока нет, поэтому промпт не требует TDD, но правила про мутационную проверку
  подстрочных assertions остаются в силе для тестов, которые агент напишет сам.
- **`BLOCKED-DB-CHANGE` вместо `BLOCKED-PROMPT-CHANGE`.** Человеческое решение здесь — не
  AI-промпты, а схема БД: `docs/**/*.sql` применяется вручную в Supabase SQL editor против того
  же проекта, на котором работает живой прод, поэтому ломающая миграция роняет приложение ещё до
  мержа PR. `docs/**` закрыт для агента через `deny` в permissions, такой issue получает лейбл
  `ralph-needs-db-change` и транзитивно блокирует всё, что от него зависит.
- **Промпт знает про прод**: `main` автодеплоится на Vercel, Supabase общий для прода и preview,
  поэтому агенту предписано предпочитать аддитивные изменения ломающим и явно помечать ломающие
  в `SUMMARY`.
- **Нет живого окружения**: ни dev-сервера, ни браузера, ни Playwright, ни реальной Supabase.
  Пункты Test Requirement, требующие живой проверки, агент обязан честно пометить
  `NOT VERIFIED` в самоотчёте, а не имитировать — их проверяет человек на Vercel preview
  до мержа PR.

## Что унаследовано без изменений

- `dependsOn` + приоритет по порядку в списке (`classify()`).
- Stacked PR для зависимых issue: зависимый ответвляется от ветки ещё не смёрженной зависимости,
  не от `main`. Репозиторий настроен на `deleteBranchOnMerge: true`, чтобы GitHub сам ретаргетил
  такой PR на `main`, когда зависимость мёрджится.
- Один комбинированный комментарий на issue при каждом `DONE`: самоотчёт по Acceptance Criteria
  + test evidence. Чек-боксы AC отмечаются автоматически **только** при полном честном
  совпадении самоотчёта со списком AC (одна строка на пункт, все `COVERED`); при частичном —
  не отмечается ничего, чтобы не выглядело более проверенным, чем есть.
- `maxIterations`/`maxTurns`/`reviewMaxTurns` — предохранители.
- Мёрдж PR всегда делает человек — контроллер только создаёт PR (`Closes #<n>`), никогда не
  мёрджит.

## Файлы

Каждый модуль отвечает ровно на один вопрос — начинай чтение с `core.js`, у него в шапке карта
всего цикла и порядок шагов `runIssue()`.

- `run.js` — точка входа: `node .claude/ralph/run.js [--max-iterations N]`. Импортирует напрямую
  из модулей-владельцев, так что слои видны прямо здесь.
- `core.js` — state machine одной итерации (`runIssue`) и бюджеты попыток. Только оркестрация:
  конкретика живёт в модулях ниже.
- `config.js` — файлы самого Ralph в `.claude/ralph/`: конфиг, снимок состояния, лок прогона.
- `github.js` — всё, что дёргает `git`/`gh`: выбор issue (`classify`), комментарии, лейблы,
  коммит, push, PR. Граница, на которой держится вся схема — у кодящего агента доступа к git/gh
  нет вообще.
- `workspace.js` — работа с клоном `.ralph-runs/issue-N`: клонирование, доверие директории,
  `npm install`, профили permissions под каждый пасс, переименования по маркеру `DEL_RALPH`.
- `prompts.js` — все тексты, которые получает агент (реализация, фикс, self-review, code-review).
- `parsing.js` — чистый разбор ответа агента (вердикты, self-report по AC) и вывода
  `git status --porcelain`. Без side-effects.
- `agent.js` — единственное место, где спавнится `claude -p` (модель/effort, stream-json).
- `config.example.json` — шаблон. Скопируй в `config.json` (гитигнорится) и отредактируй список
  `issues`.

Зависимости однонаправленные: `run.js` → `core.js` → {`github`, `workspace`, `prompts`,
`parsing`, `agent`}, и отдельно `workspace` → {`github`, `parsing`, `config`}. Циклов нет.

Рантайм-файлы (все гитигнорены):
- `.claude/ralph/config.json` — реальный список задач.
- `.claude/ralph/state.json` — снимок последнего прогона (диагностика, не источник правды —
  источник правды всегда GitHub).
- `.claude/ralph/run.lock` — PID активного прогона; второй экземпляр стартовать откажется.
- `.ralph-runs/issue-<n>/` — клон репозитория под конкретный issue. Удаляется при успехе и при
  `BLOCKED`; **оставляется** при сбое — путь печатается в лог для разбора.

## Запуск

```bash
cp .claude/ralph/config.example.json .claude/ralph/config.json
# отредактируй issues под актуальную задачу
node .claude/ralph/run.js --max-iterations 1
```

Требования: `gh` авторизован (`gh auth status`), `claude` CLI в PATH, у issue заполнено тело по
формату из `.claude/skills/issues/SKILL.md` (иначе агенту нечего реализовывать, а контроллеру
нечего сверять в разделе `## Acceptance Criteria`).
